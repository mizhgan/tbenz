# Топливо — трекер доступности топлива на АЗС

Приложение опрашивает публичный источник данных `toplivo.tbank.ru` по заданным
районам (bounding box), сохраняет полученные данные о заправках в MongoDB и
хранит историю по каждой станции, чтобы её можно было посмотреть в
исторической перспективе на карте. Публичной части нет — только защищённая
логином админка на Vue.

## О данных источника

Важно: источник отдаёт **не цены**, а статус доступности топлива по каждому
виду топлива, судя по всему выведенный из недавних транзакций по карте:
`available` / `maybe_available` / `not_available` / `no_data`, плюс время
последней транзакции (`lastTransactionAt`). Схема подтверждена на реальном
ответе API:

```json
{
  "status": "ok",
  "payload": [
    {
      "id": "01KWEMF0Y2M5WC0FZY7F94RA18",
      "name": "Лукойл",
      "addr": "Россия, Киров, Нововятский район, Советская улица, 174А",
      "lat": 58.484922,
      "lon": 49.737982,
      "status": "available",
      "statusByFuelType": { "92": "available", "95": "maybe_available" },
      "yandexOrgId": "10142079165",
      "lastTransactionAt": "2026-07-07T06:02:19.091Z"
    }
  ]
}
```

Разбор реализован в `backend/src/services/stationParser.js` и покрыт
юнит-тестом на этом примере. Полный «сырой» JSON станции всё равно
сохраняется целиком (`Station.lastRaw`, `StationSnapshot.raw`) — на случай,
если у части станций (например, АГЗС/АГНКС) появятся другие коды видов
топлива или дополнительные поля.

## Стек

- **Backend**: Node.js, Express, MongoDB (Mongoose), JWT-аутентификация,
  собственный планировщик на `setInterval` с настраиваемым интервалом на
  каждый район.
- **Frontend**: Vue 3 (Composition API, `<script setup>`), Vite, Pinia,
  Vue Router, Leaflet (карта), Chart.js (график истории статусов), gif.js +
  leaflet-image + MediaRecorder (экспорт GIF/видео-анимации, полностью на
  клиенте).
- **База данных**: MongoDB.

## Возможности админки

- Логин по паролю (JWT), две роли:
  - **admin** — полный доступ: районы (CRUD, ручной опрос), пользователи, карта, отчёты.
  - **viewer** (наблюдатель) — только просмотр: карта, отчёты, детали и прогноз
    станций. Пункты меню «Районы» и «Пользователи» для наблюдателя скрыты, а
    прямой переход по URL на эти страницы перенаправляет на карту — доступ
    закрыт и на уровне API (`requireAdmin` возвращает 403 на мутирующих
    эндпоинтах районов и на всех `/api/users/*`), не только в интерфейсе.
  - Пользователей (логин/пароль/роль) заводят и редактируют только
    администраторы, на странице «Пользователи». Есть защита от блокировки:
    нельзя удалить себя и нельзя удалить или понизить последнего администратора.
- Управление районами отслеживания (только для admin): добавление/редактирование/удаление,
  задание границ прямоугольника на карте (два клика) или вручную по
  координатам, включение/выключение, свой интервал опроса по крону в минутах.
  Плюс кнопка «Опросить сейчас» для ручного запроса вне расписания.
  Список районов обновляется автоматически, показывает статус последнего
  опроса и число найденных станций.
- Карта станций, окрашенных по статусу доступности топлива, со слайдером по
  времени (обновляется прямо при перетаскивании, без ожидания отпускания),
  фильтрами по статусу (по умолчанию скрыты станции без данных), фильтром по
  сети/бренду (поле `name` источника) — выпадающий список с поиском и
  кнопками «Все»/«Ничего»; список сетей строится из реально загруженных
  станций, а выбор не сбрасывается при обновлении снимка (слайдер, живой
  режим), только при смене района — и фильтром по виду топлива (выпадающий
  список АИ-92/95/98/... строится из реально встреченных `fuelType`). Когда
  выбран конкретный вид топлива, чекбоксы статуса и цвет маркера на карте
  переключаются с общего статуса станции на статус именно этого вида
  топлива; станция, которая вообще не сообщает о выбранном виде топлива,
  считается «нет данных» для него (и по умолчанию скрыта, как и обычная
  «нет данных»). Все фильтры действуют и на кадры экспорта анимации. Карта
  занимает всю ширину страницы (нет постоянной боковой панели, отъедающей
  место) и выше по умолчанию, чем раньше — раньше она растягивалась только
  под высоту соседней панели, теперь у неё собственная, увеличенная
  минимальная высота. Клик по станции открывает всплывающее окно прямо на
  маркере (`marker.bindPopup`, содержимое собирается как HTML-строка в
  `buildPopupHtml()` — попап живёт вне дерева рендера Vue, поэтому все
  подставляемые в него значения из данных источника — название, адрес, вид
  топлива — экранируются вручную через `escapeHtml()`, а не рендерятся Vue
  автоматически): статус, компактный список видов топлива, время последней
  транзакции и кнопка «Подробная информация», открывающая то же модальное
  окно, что и раньше —
  мини-карта станции, статистика надёжности за последние 7 дней (доступность,
  доля "нет данных", число отключений, среднее время восстановления — тот же
  `GET /regions/:id/metrics/stations`, что и на странице отчётов), прогноз на
  ближайшие часы и график истории по видам топлива.
- Сводка «Текущее состояние» — не отдельная карточка, а компактная строка
  прямо в панели фильтров (под чекбоксами статуса): доля доступности прямо
  сейчас и разбивка станций по статусам (доступно/частично/нет/нет данных)
  для выбранного района, плюс количество показанных станций из общего числа
  — то же самое, что уже красит маркеры на карте, просто в виде чисел, а не
  точек и не отдельной карточки с занимаемым ей местом. Считается из уже
  загруженных на странице станций, теми же правилами, что и цвет маркеров
  (`effectiveStatus`), поэтому никогда не расходится с картой, включая
  момент времени (если слайдер отмотан назад — сводка тоже за тот момент, а
  не за «сейчас» по часам) и выбранный вид топлива (если выбран конкретный
  вид топлива, сводка тоже переключается на доступность именно этого вида,
  как и цвет маркеров). Не учитывает чекбоксы статуса/сети — те скрывают
  маркеры для удобства чтения карты, но не должны менять то, что считается
  фактическим состоянием района.
- Настройка цветов видов топлива (страница «Настройки», доступна любой роли
  — это личная настройка отображения, а не данные): график истории станции
  рисует по одной линии на вид топлива (`StationHistoryChart.vue`), и цвет
  каждой линии можно поменять через `<input type="color">`. Список видов
  топлива строится по данным реальных снимков всех районов (плюс уже
  сохранённые кастомные цвета, даже если сейчас этот вид топлива не
  встретился, и вручную добавленные типы). Без кастомизации цвет
  берётся детерминированно по хэшу названия вида топлива (FNV-1a) из
  фиксированной палитры — один и тот же вид топлива всегда получает один и
  тот же цвет по умолчанию, независимо от того, какие ещё виды топлива есть
  у конкретной станции. Хранится только в `localStorage` браузера (ключ
  `fuelColors`, JSON `{ "92": "#rrggbb", ... }`) через Pinia-стор
  `useFuelColorsStore` — это личная настройка отображения, у каждого
  пользователя и на каждом устройстве она своя, на сервер не отправляется.
- Карточка станции для шаринга (кнопка в модалке «Подробная информация»):
  собирает статус, строку с прогнозом восстановления (если станция сейчас
  недоступна — тот же расчёт, что и в блоке «Прогноз на ближайшие часы»),
  список видов топлива, статистику надёжности за 7 дней и компактную историю
  по каждому виду топлива (горизонтальная полоса из цветных сегментов —
  статус в каждый момент времени, без осей и легенды, как у полноценного
  графика: тут важно охватить взглядом, а не анализировать) в одну
  PNG-картинку, полностью на `<canvas>` в браузере — без скриншотов DOM,
  сторонних библиотек и обращений к бэкенду сверх уже загруженных на странице
  данных (прогноз и история дозапрашиваются в момент генерации картинки,
  `Promise.allSettled` — если что-то из этого не загрузится, картинка всё
  равно соберётся, просто без этого блока). Высота подбирается под реальное
  содержимое (мало видов топлива — картинка компактнее), а не фиксирована.
  Главная кнопка — «Скопировать в буфер»: в отличие от видео (см. ниже),
  копирование PNG в буфер обмена браузеры поддерживают
  (`ClipboardItem` с `image/png`) — проверено эмпирически в headless
  Chromium полным циклом запись→чтение, а не только вызовом без ошибок.
  Плюс обычные «Скачать» и «Поделиться» (`navigator.share` с файлом), когда
  доступны.
- Экспорт анимации (GIF или видео WebM/MP4) по выбранному промежутку времени:
  показывает, как менялись статусы станций на карте кадр за кадром (с учётом
  текущих фильтров). Один кадр — один реально сохранённый опрос района
  (`GET /regions/:id/snapshot-times`), без интерполяции между произвольными
  точками времени; если снимков больше заданного лимита, они равномерно
  прореживаются, а не подменяются вычисленными датами. Кодируется полностью в
  браузере (gif.js через Web Worker для GIF, MediaRecorder для видео), без
  обращения к бэкенду сверх обычных запросов снимков. Видео заметно легче GIF
  при том же содержимом и удобнее
  для отправки в Telegram (он сам проигрывает такие короткие беззвучные
  видео как анимацию). Есть кнопка «Поделиться» через `navigator.share`,
  когда браузер/ОС её поддерживают — иначе доступна обычная кнопка
  «Скачать». Прямого копирования видео в буфер обмена нет ни у одного
  браузера — это ограничение Clipboard API, а не что-то, что можно обойти
  (в отличие от статичных PNG-картинок — см. карточку станции выше, там
  копирование в буфер работает).
- Отчёты по району за произвольный период (пресеты 24ч/7д/30д, свои даты — по
  выбору даты отчёт обновляется автоматически): KPI-плитки (общая
  доступность, число станций, отключений, среднее время восстановления),
  график динамики доступности по времени (stacked area:
  доступно/возможно доступно/недоступно), таблица топ-5 станций с
  переключателем «Лучшие/Худшие» (по умолчанию — лучшие), полная сортируемая
  таблица по всем станциям, сравнение средней доступности по сетям/брендам
  (по полю `name` источника) и тепловая карта доступности по дню недели/часу
  — показывает, например, что топливо чаще пропадает по утрам перед
  подвозом. Секции отчёта загружаются независимо: если один из запросов
  метрик не отвечает, это не блокирует остальные — сломавшаяся секция
  покажет свою ошибку, а не молча оставит старые данные от предыдущего
  периода. Название станции в обеих таблицах (топ-5 и полная) — кликабельная
  ссылка, открывающая ту же модалку «Подробная информация», что и карта
  (мини-карта, полный список видов топлива, надёжность, прогноз, история,
  карточка для шаринга). Эндпоинты метрик отчётов отдают только агрегаты
  (без координат и текущего статуса станции), поэтому по клику отдельно
  подгружается сам документ станции (`GET /api/stations/:id`) и приводится к
  тому же виду, в котором его ожидает модалка на карте (`lastStatus` →
  `status`, `lastFuelStatuses` → `fuelStatuses`, `lastSeenAt` → `polledAt`).
- Картинка отчёта для шаринга (кнопка «Сгенерировать картинку» на странице
  «Отчёты», `frontend/src/utils/regionReportCard.js`): название района и
  период (дата указывается на обеих границах периода, а не только время —
  иначе ровно 24-часовой период показывал бы визуально неотличимые
  «18:15–18:15»), те же 4 KPI-плитки, что и на странице, график динамики
  доступности — те же три цвета статусов, что и в полном графике на странице
  (`TrendChart.vue`) и в остальном приложении: зелёная область (доступно),
  жёлтая (возможно доступно) и красная (недоступно), стек друг на друге, а
  не одна произвольно окрашенная линия тренда — цвет линии на графике
  доступности обязан значить именно доступность, а не совпадать с цветом
  индикатора направления рядом. Пунктирная синяя линия — продолжение
  прогноза (тот же `trend-forecast`, что уже загружен для графика на
  странице), если он есть. Разрывы в данных заполняются ближайшим известным
  значением (как `spanGaps: true` у графика на странице), а не обрываются —
  карточка должна читаться как «тот же график, только компактнее». Отдельно
  от самого графика — стрелка направления и изменение от начала к концу
  периода текстом под ним, и топ-3 станции текущей вкладки
  (лучшие или худшие — какая открыта на странице в этот момент). Сравнение
  по сетям и тепловая карта в картинку сознательно не включены — отчёт и
  так весь не поместился бы компактно, лучше показать сводку, а не
  попытаться втиснуть каждую секцию. Как и карточка станции (кнопка в карте
  → «Подробная информация»), это чистый Canvas 2D на клиенте: высота
  подбирается под реальное содержимое (два прохода — сначала измерить, потом
  нарисовать, чтобы отчёт без топ-станций или без данных для графика не
  доставлял картинку с пустым местом), без обращений к бэкенду сверх уже
  загруженных на странице данных. Те же самые кнопки «Скопировать в
  буфер»/«Скачать»/«Поделиться», что и у карточки станции — реализация (и
  разметка CSS `.card-preview`/`.card-actions`) общая для обеих карточек.
- Прогнозирование (простое, без ML): на странице отчётов — линейная
  экстраполяция тренда доступности региона на несколько шагов вперёд с
  меткой направления (улучшается/стабильно/ухудшается), нарисованная
  пунктиром продолжением графика. На карте, при выборе станции — прогноз
  доступности на ближайшие 12 часов по её собственному историческому
  профилю "день недели + час", и если станция сейчас недоступна — оценка
  времени восстановления на основе среднего времени простоя этой станции в
  прошлом.
- Управление прокси для запросов к источнику данных (только для admin,
  страница «Прокси»): добавление (HTTP/HTTPS/SOCKS5, адрес, порт, логин/пароль
  по желанию), ручная проверка соединения одним кликом, включение/выключение,
  удаление. Пароль прокси никогда не возвращается обратно в API-ответах — в
  списке показывается только факт, что он задан (`hasPassword`). Пока есть
  хотя бы один активный прокси, каждый опрос источника данных случайно
  выбирает один из них; при ошибке запроса прокси помечается и делается
  повторная попытка с другим случайным активным прокси (до 5 попыток за
  опрос). После нескольких ошибок подряд (по умолчанию 3,
  `PROXY_FAILURE_THRESHOLD`) прокси отключается автоматически, чтобы не
  продолжать безуспешно долбиться в него на каждом опросе — это видно в
  таблице как причина отключения и счётчик ошибок подряд. Таблица также
  показывает счётчик запросов через каждый прокси за всё время (успешно/с
  ошибкой) — видно, насколько равномерно распределяется нагрузка и какой
  прокси реально используется. Если активных прокси не настроено (или все
  они выключены), запросы идут напрямую, как и раньше.
- Telegram-бот (только для admin, страница «Telegram»): уведомляет выбранные
  чаты/группы о появлении и исчезновении топлива на станциях, а также
  присылает часовые/дневные сводки по районам. Бот работает в личных чатах,
  группах и супергруппах через long polling (`telegraf`), отдельный публичный
  HTTPS-эндпоинт не требуется. Модель безопасности намеренно двухступенчатая:
  любой чат, куда добавили бота (или который просто написал ему что-то),
  автоматически регистрируется в статусе «ожидает настройки» — но реально
  получать уведомления чат начинает только после того, как администратор
  вручную переведёт его в статус «активен» и настроит районы/события на
  странице «Telegram». Простая переписка с ботом сама по себе никогда не даёт
  чату доступ к каким-либо данным. В группах и супергруппах регистрация не
  зависит от того, напишет ли кто-нибудь боту сообщение: по умолчанию у ботов
  в группах включён Privacy Mode, из-за которого Telegram не доставляет боту
  обычные сообщения участников (только команды, упоминания бота и ответы на
  его сообщения) — сам факт добавления бота в группу приходит отдельным
  событием `my_chat_member`, которое не подчиняется Privacy Mode, и именно на
  него подписан бот, поэтому чат появляется в списке сразу после добавления,
  ещё до того, как в группе кто-то что-то написал. На чат можно настроить: список районов
  (чат может следить сразу за несколькими), какие события присылать
  (появление топлива / исчезновение топлива / часовая сводка / дневная
  сводка / прогнозные алерты — см. отдельный пункт ниже), фильтр по видам
  топлива и по сети/бренду для событий
  появления/исчезновения (пусто — все), и отдельный вотчлист конкретных
  станций (поиск по названию/адресу через `GET /api/stations?q=`) — станции
  из вотчлиста уведомляют чат независимо от фильтров по виду топлива/бренду.
  Событие «появилось»/«пропало» определяется сравнением статуса каждого вида
  топлива на станции до и после очередного опроса района
  (`available`/`maybe_available` считаются «есть», `not_available` — «нет»);
  первое наблюдение вида топлива на станции событием не считается — сравнивать
  не с чем. Уведомления о появлении/исчезновении топлива группируются на двух
  уровнях, а не отправляются по одному: если у станции одновременно
  изменилось несколько видов топлива — это один блок в сообщении, а не
  отдельное сообщение на каждый вид; если в рамках одного опроса района
  изменилось сразу несколько станций — это тоже одно сообщение (или
  несколько, если общий текст не помещается в лимит Telegram на длину
  сообщения — тогда режется на части, но всё равно на порядок компактнее, чем
  сообщение на каждую станцию). Группировка — по конкретному опросу
  конкретного района: разные районы опрашиваются по своему расписанию
  независимо, поэтому их изменения в одно сообщение не объединяются.
  Часовые/дневные сводки не завязаны на конкретное время суток —
  планировщик проверяет каждые 5 минут, не истёк ли у чата его собственный интервал
  с прошлой сводки (`lastHourlyDigestAt`/`lastDailyDigestAt`), поэтому механизм
  переживает перезапуск бэкенда без потери расписания и без выравнивания по
  cron. Кнопка «Тест» на странице «Telegram» отправляет чату одно тестовое
  сообщение вне расписания, чтобы проверить, что бот действительно может
  писать в этот чат. Если переменная окружения `TELEGRAM_BOT_TOKEN` не
  задана, весь функционал бота полностью неактивен (бот не запускается,
  сборка событий и отправка сводок no-op) — так же, как прокси-пул работает
  как опциональная функция.
- Самостоятельная настройка рассылки в личных чатах (`telegramSettingsMenu.js`,
  команда `/settings`): человек, который написал боту напрямую (не в группе),
  может сам выбрать районы, включить/выключить каждое из событий и вести свой
  вотчлист станций через inline-меню в переписке с ботом — без обращения к
  администратору и без веб-панели. Кнопка «⚙️ Настроить рассылку» приходит
  сразу в ответ на `/start`, а `/settings` открывает то же меню в любой
  момент. Специально ограничено личными чатами (`chat.type === 'private'`):
  добавить бота в группу может кто угодно, и если бы самостоятельная
  настройка работала и там, любой участник группы мог бы менять рассылку для
  всех остальных — для групп/супергрупп настройка по-прежнему только через
  админ-панель. Меню — не полный паритет с админкой: районы, 6 событий и
  вотчлист станций (поиск текстом прямо в чате, до 8 совпадений по
  названию/адресу за раз), а вот фильтры по видам топлива и по сети/бренду
  остались только в веб-форме (`TelegramChatForm.vue`) — самый частый сценарий
  для личного чата и так покрыт, а свободный ввод произвольных списков через
  inline-кнопки менее удобен, чем текстовое поле в админке. Двухступенчатая
  модель безопасности (пока админ не активирует чат — уведомления не идут)
  для личных чатов при этом меняется на самоактивацию: кнопка
  «🔔 Включить рассылку»/«⏸ Приостановить рассылку» в меню сама переключает
  статус чата между `active` и `disabled`, без участия администратора — это
  осознанное решение только для личных чатов (см. обоснование выше про
  группы), администратор по-прежнему видит и может отключить любой чат из
  веб-панели в любой момент. Вся навигация построена на inline-кнопках
  (`callback_data` вида `settings:...`), которые редактируют одно и то же
  сообщение-меню (`editMessageText`) вместо потока новых сообщений; текстовый
  ввод используется только для поиска станции в вотчлист — состояние "ожидаю
  текст поиска" держится в памяти процесса (`Map` по chatId), без отдельной
  таблицы в БД, поскольку это одноразовый флаг на сессию переписки, а не
  постоянные данные. Названия районов/станций, попадающие в текст
  сообщения-меню (не в подписи самих кнопок — те не парсятся Telegram как
  HTML и экранирования не требуют), экранируются так же, как и везде в
  Telegram-уведомлениях этого бота.
- Прогнозные алерты (`telegramPredictiveAlerts.js`, `telegramPredictiveScheduler.js`) —
  два отдельных, по умолчанию выключенных события: «скоро может пропасть» и
  «скоро может появиться» — предупреждение до того, как топливо реально
  пропало/появилось, а не постфактум. Основано на том же историческом
  профиле "день недели + час" по станции, что уже используется в прогнозе
  на карте (`forecastService.js`): для станций, у которых сейчас топливо
  есть, каждые 30 минут проверяется прогноз на ближайшие 2 часа — если хотя
  бы на один из этих часов историческая вероятность падает ниже 30%,
  чат получает предупреждение с конкретным часом и предсказанным %; для
  станций, где топлива сейчас нет, оценка времени восстановления (по
  среднему времени простоя станции в прошлом) сравнивается с окном в 1 час
  вперёд — если восстановление ожидается в течение часа (и оно ещё
  впереди, а не "уже должно было случиться"), чат получает уведомление.
  Действует на **весь отслеживаемый район**, а не только на вотчлист — при
  таком охвате пересчёт прогноза для каждой станции по отдельности на каждой
  проверке был бы слишком дорог по ресурсам БД, поэтому для станций "топливо
  есть" (обычно большинство) исторический профиль считается одной bulk-
  агрегацией сразу по всем таким станциям района (`getBulkHourlyProfiles`),
  а не отдельным запросом на станцию; поштучные запросы (оценка времени
  восстановления) остаются только для станций, где топлива сейчас нет —
  на практике таких обычно меньшинство. Чтобы не слать одно и то же
  предупреждение на каждой 30-минутной проверке, пока прогноз остаётся
  тревожным, у каждой станции есть троечасовой "кулдаун" на алерт каждого
  типа (`Station.lastPredictiveDropAlertAt`/`lastPredictiveRecoveryAlertAt`) —
  повторно предупредить о той же станции можно не раньше чем через 3 часа
  после предыдущего алерта такого типа. Это простая эмпирическая оценка по
  прошлым данным (как и весь `forecastService.js`), а не обученная модель —
  см. предостережения в разделе «Как считается прогноз» ниже.
- Часовая/дневная сводка — картинка на район с текстом-подписью, одним
  постом (`telegramDigestData.js`, `telegramDigestImage.js`): для чата с
  одним районом отправляется одно фото, с несколькими — альбом (Telegram
  требует минимум 2 фото для альбома, поэтому одно фото шлётся отдельно, не
  через `sendMediaGroup`). Текст идёт не отдельным сообщением, а подписью
  (`caption`) к первому фото в альбоме/фото — так весь дайджест приходит в
  чат одним постом, а не картинкой и сообщением по отдельности. У подписи к
  фото лимит Telegram всего 1024 символа (у обычного сообщения — 4096),
  поэтому подпись собирается из целых секций по одному району за раз и
  останавливается, если следующая секция не помещается целиком — так лимит
  никогда не обрежет HTML-тег на середине (что сломало бы отправку с
  `parse_mode=HTML`); при этом все картинки по всем районам чата отправляются
  в любом случае, обрезается только сопроводительный текст. Картинка
  рендерится на бэкенде из SVG через `sharp` (без headless-браузера и без
  `node-canvas` — оба варианта либо тяжелее в развёртывании, либо требуют
  нативной компиляции; `sharp` ставится готовым бинарником даже под Alpine).
  На картинке — крупный % доступности прямо сейчас (не средний за период,
  цвет по порогам 85%/60%), разбивка станций сейчас
  (доступно/частично/нет/нет данных), стрелка тренда по сравнению с таким же
  предыдущим периодом, мини-график (спарклайн) динамики за период —
  минутные бакеты с явным заполнением пропусков (`getAvailabilitySeries`),
  чтобы дырки в данных рисовались разрывом линии, а не воспринимались как
  0%, и подпись `tbenz.in` в углу. В подписи к фото — то, что не умещается в
  картинку компактно: точное число отключений за период и топ-3 самых
  доступных станций за период с адресом и процентом доступности (станции,
  где топливо реально можно найти, а не только "где сейчас плохо"). Эмодзи-
  иконки (🟢🟡🔴) в самой картинке не используются — цветные эмодзи в
  headless-рендеринге через `librsvg` превращаются в закрашенные точки без
  цвета (нет шрифта цветных эмодзи), это выяснилось эмпирически при
  рендеринге тестовых карточек; вместо них — обычные закрашенные SVG-кружки
  нужного цвета. В текстовых уведомлениях о появлении/исчезновении топлива
  (не в картинке сводки) эмодзи по-прежнему используются как раньше — их
  рисует клиент Telegram, а не сервер.
- Адаптивность под мобильные экраны: карта — не единственный столбец рядом с
  боковой панелью (той больше нет, см. выше), а обычный блок на всю ширину
  страницы, поэтому схлопывать нечего; на узких экранах уменьшается только
  её минимальная высота. В отчётах и на других
  страницах с таблицами (районы, пользователи, прокси) таблицы скроллятся
  горизонтально внутри себя, а не тянут за собой всю страницу — исправлена
  типичная grid/flex-ловушка, когда дочерний элемент по умолчанию не
  сжимается уже собственного контента (`min-width: auto`), из-за чего
  `overflow-x: auto` на обёртке таблицы попросту не срабатывал. Верхнее меню
  на узких экранах переносится под шапку отдельной строкой и скроллится по
  горизонтали, если не помещается целиком.

docker compose up --build

## Модель данных (MongoDB)

- **Region** — отслеживаемый район: название, `minLat/maxLat/minLon/maxLon`,
  `pollIntervalMinutes`, `active`, статус последнего опроса.
- **Station** — физическая АЗС, дедуплицированная по `externalId` (могут
  входить в несколько районов, если их bbox пересекаются). Хранит последнее
  известное состояние (`lastStatus`, `lastFuelStatuses`, `lastTransactionAt`,
  `lastRaw`, `lastSeenAt`), а также `lastPredictiveDropAlertAt`/
  `lastPredictiveRecoveryAlertAt` — метки кулдауна прогнозных Telegram-алертов
  (когда в последний раз предупреждали об этой станции, чтобы не слать
  повторно на каждой проверке).
- **StationSnapshot** — историческая запись: одна запись на станцию на каждый
  опрос района (`polledAt`, `status`, `fuelStatuses`, `lastTransactionAt`,
  `raw`). Именно эта коллекция используется для слайдера времени на карте и
  графика истории статусов. Индексы покрывают выборку "последний снимок на
  станцию до момента X" и выборку по станции.
- **User** — логин, хэш пароля, роль (`admin` | `viewer`). Роль в JWT не
  считается источником истины: `requireAuth` на каждый запрос перечитывает её
  из этой коллекции по `sub` из токена (подробнее — в разделе «Известные
  ограничения»).
- **Proxy** — прокси для запросов к источнику данных: тип (`http` | `https` |
  `socks5`), адрес, порт, логин/пароль (по желанию), `active`,
  `consecutiveFailures` (сбрасывается при успехе, копится при ошибках),
  `disabledReason` (причина автоотключения), плюс отдельные поля
  `lastCheck*` для результата ручной проверки — они не участвуют в счётчике
  автоотключения, это независимая диагностика. Отдельно от
  `consecutiveFailures` копятся счётчики за всё время: `totalRequests`,
  `successCount`, `failureCount` — не сбрасываются при успешном запросе (в
  отличие от `consecutiveFailures`) и не учитывают ручные проверки
  («Проверить»), только реальные запросы к источнику данных.
- **TelegramChat** — Telegram-чат/группа, известная боту: `chatId` (ID чата в
  Telegram, строкой), `title`, `type` (`private`/`group`/`supergroup`/
  `channel`), `status` (`pending`/`active`/`disabled` — уведомления реально
  уходят только при `active`), список `regions` (за какими районами следит),
  `events` (флаги `stationAvailable`/`stationUnavailable`/`hourlyDigest`/
  `dailyDigest`/`predictiveDropAlert`/`predictiveRecoveryAlert`), фильтры
  `fuelTypes`/`brands` для событий по станциям (пустой массив — без фильтра,
  все), `watchlist` (список станций, уведомляющих чат независимо от
  `fuelTypes`/`brands`), и `lastHourlyDigestAt`/`lastDailyDigestAt` — когда
  чату в последний раз отправлялась соответствующая сводка (по ним
  планировщик решает, не пора ли снова).

## Основные API-эндпоинты (все, кроме `/auth/login`, требуют `Authorization: Bearer <token>`; отмеченные 🔒 — только для роли `admin`, иначе 403)

- `POST /api/auth/login` — логин, возвращает JWT (полезная нагрузка включает роль).
- `GET /api/auth/me` — текущий пользователь (id/username/role) по токену.
- `GET /api/regions` — список районов (любая роль).
- 🔒 `POST /api/regions`, `PUT/DELETE /api/regions/:id`, `POST /api/regions/:id/poll` — CRUD районов и ручной опрос.
- `POST /api/regions/:id/poll` — опросить район прямо сейчас.
- `GET /api/regions/:id/history-range` — диапазон дат, за который есть история (для границ слайдера).
- `GET /api/regions/:id/snapshot-times?from=&to=` — список точных моментов
  опроса (`polledAt`), реально сохранённых для района в диапазоне; используется
  экспортом анимации, чтобы кадры строились из фактических снимков, а не из
  произвольных равномерных точек времени.
- `GET /api/regions/:id/snapshot?at=<ISO-дата>` — состояние всех станций района
  на заданный момент (последний снимок ≤ `at` на каждую станцию); без `at` —
  фактически текущее состояние.
- `GET /api/stations?q=&region=&limit=` — поиск станций по названию/адресу
  (регистронезависимая подстрока), опционально в рамках района; используется
  вотчлистом на странице «Telegram» (любая роль, лимит по умолчанию 20, максимум 100).
- `GET /api/stations/:id` — карточка станции.
- `GET /api/stations/:id/history?from=&to=&limit=` — временной ряд статусов по станции.
- `GET /api/regions/:id/metrics/trend?from=&to=&bucketHours=` — динамика доли
  доступных/возможно доступных/недоступных станций по времени, забакетовано
  (`$dateTrunc`, часовой пояс `Europe/Moscow` по умолчанию).
- `GET /api/regions/:id/metrics/stations?from=&to=` — надёжность по каждой
  станции: доля доступности, доля "нет данных", число отключений и среднее
  время восстановления.
- `GET /api/regions/:id/metrics/brands?from=&to=` — то же самое агрегировано
  по полю `name` станции (сеть/бренд).
- `GET /api/regions/:id/metrics/heatmap?from=&to=&tz=` — средняя доступность
  по ISO-дню недели (1=Пн..7=Вс) и часу суток (`$dateToParts`).
- `GET /api/regions/:id/metrics/trend-forecast?from=&to=&bucketHours=&bucketsAhead=` —
  линейная экстраполяция тренда доступности региона на `bucketsAhead`
  бакетов вперёд (по умолчанию 6) плюс метка направления
  (`improving`/`worsening`/`stable`/`unknown`).
- `GET /api/stations/:id/forecast?hoursAhead=&lookbackDays=&tz=` — прогноз
  доступности станции на `hoursAhead` часов вперёд (по умолчанию 24) по её
  историческому профилю "день недели + час" за последние `lookbackDays` дней
  (по умолчанию 28), плюс оценка времени восстановления, если станция сейчас
  недоступна.
- 🔒 `GET/POST /api/users`, `PUT/DELETE /api/users/:id` — управление
  пользователями: список, создание (логин/пароль/роль), смена роли/пароля,
  удаление. Нельзя удалить/понизить последнего администратора и нельзя
  удалить собственную учётную запись.
- 🔒 `GET/POST /api/proxies`, `PUT/DELETE /api/proxies/:id` — управление
  списком прокси: список (без паролей — только флаг `hasPassword`),
  добавление, изменение (тип/адрес/порт/логин/пароль/`active`), удаление.
- 🔒 `POST /api/proxies/:id/check` — разовая проверка соединения через этот
  прокси (запрос к `PROXY_CHECK_URL`); результат (успех/ошибка, задержка)
  сохраняется в `lastCheck*` и не влияет на счётчик автоотключения.
- 🔒 `GET /api/telegram/status` — состояние бота: включён ли
  (`TELEGRAM_BOT_TOKEN` задан), запущен ли long polling, username бота.
- 🔒 `GET /api/telegram/chats` — список известных боту чатов со всеми
  настройками (районы и станции вотчлиста возвращаются с именами, не только ID).
- 🔒 `PUT /api/telegram/chats/:id` — частичное обновление настроек чата
  (`status`/`regions`/`events`/`fuelTypes`/`brands`/`watchlist`); `events`
  сливается с уже сохранёнными флагами, а не заменяет их целиком.
- 🔒 `DELETE /api/telegram/chats/:id` — убрать чат из списка (сам бот при этом
  из чата не выходит; если чат снова что-то напишет боту, он будет
  зарегистрирован заново в статусе «ожидает настройки»).
- 🔒 `POST /api/telegram/chats/:id/test` — отправить чату одно тестовое
  сообщение вне расписания (годится только для чатов в статусе `active`, у
  которых бот уже может писать в чат).

## Как считаются метрики отчётов

Реализация — `backend/src/services/metricsService.js`.

- **Доля доступности** считается от числа снимков с известным статусом
  (`available` + `maybe_available` + `not_available`), **исключая**
  `no_data` — иначе станции с редкими транзакциями (и поэтому большой долей
  `no_data`) выглядели бы незаслуженно ненадёжными. Доля `no_data` показана
  отдельно как сигнал качества данных по станции.
- **Отключение (outage)** — непрерывный период статуса `not_available`,
  начинается на первом снимке с этим статусом и заканчивается на следующем
  снимке `available`/`maybe_available`. Снимки `no_data` внутри отключения
  его не завершают (статус неизвестен, ждём дальше). Отключение, которое не
  закончилось до конца выбранного периода, в статистику не попадает — его
  реальная длительность неизвестна ("цензурировано" в терминах анализа
  выживаемости).
- **Среднее время восстановления** — среднее по длительностям завершившихся
  отключений станции.
- Группировка по сети/бренду использует поле `name` станции как есть (это
  поле источника, не выделенный отдельно бренд — для части АЗС там может
  быть просто "АЗС" или собственное имя объекта).

Логика подсчёта отключений (`computeOutages`) покрыта юнит-тестом на
синтетических историях (чистое отключение, `no_data` внутри отключения,
незакрытое отключение, несколько отключений подряд) — см. предупреждение
ниже про то, что сами агрегации Mongo (`$group`/`$dateTrunc`/`$dateToParts`)
не проверялись на реальной базе.

## Как считается прогноз

Реализация — `backend/src/services/forecastService.js`. Оба вида прогноза —
простая статистика по прошлым данным, а не обученная модель; ниже честно
описано, что это означает на практике.

- **Прогноз по станции** — эмпирическая вероятность: для каждого часа из
  ближайших `hoursAhead` определяется его (день недели, час) в заданном
  часовом поясе, и берётся историческая доля `available` среди снимков
  станции в этот же (день недели, час) за последние `lookbackDays` дней. Если
  для конкретного слота истории ещё нет — используется общее среднее по
  станции. Предположение здесь простое: "как было в этот день недели и час
  раньше, так, скорее всего, будет и в следующий раз" — это разумное, но не
  гарантированное допущение (не учитывает форс-мажоры вроде разовых перебоев
  с поставками).
- **Оценка времени восстановления** — момент начала текущего отключения (по
  истории статусов) плюс среднее историческое время восстановления той же
  станции (`computeOutages` за `lookbackDays`). Если станция ни разу не
  восстанавливалась за это окно — оценка не показывается.
- **Прогноз тренда по региону** — обычная линейная регрессия (метод
  наименьших квадратов) по последним точкам графика доступности, продолженная
  на `bucketsAhead` бакетов вперёд и обрезанная в диапазон [0, 100]%.
  Направление (`improving`/`worsening`/`stable`) определяется порогом наклона
  в 1 процентный пункт за бакет. Это **не** полноценная модель временных
  рядов — нет сезонности, нет доверительного интервала, только грубый сигнал
  "тренд идёт вверх/вниз/плоско", и он не защищён от резких разовых скачков
  в последних точках данных.

Функции `linearRegression` и `isoWeekdayAndHour` (перевод момента времени в
день недели/час в заданном часовом поясе, включая переход через полночь)
покрыты юнит-тестами на синтетических данных.

## Планировщик

Реализован в `backend/src/services/scheduler.js`: при старте сервера
загружаются все активные районы и на каждый ставится `setInterval` с его
собственным `pollIntervalMinutes`. При создании/изменении/удалении района
через API расписание пересобирается на лету — перезапуск сервера не требуется.
При создании нового района первый опрос запускается сразу же, не дожидаясь
первого тика интервала.

Отдельно от опроса районов — два Telegram-специфичных планировщика с
собственным интервалом, не завязанным на `pollIntervalMinutes` конкретного
района: `telegramDigestScheduler.js` (каждые 5 минут проверяет, не пора ли
кому-то из чатов часовую/дневную сводку) и `telegramPredictiveScheduler.js`
(каждые 30 минут пересканирует все активные районы на прогнозные алерты).
Оба, как и опрос районов, запускаются сразу при старте, а не ждут первого
тика.

## Известные ограничения / что стоит сделать дальше

- Компоненты графиков (`TrendChart.vue`, `BrandsChart.vue`, `StationHistoryChart.vue`)
  никогда не вешают `v-show` прямо на `<canvas>` — только на оборачивающий
  `<div>`. Это не стилистический выбор: Chart.js при создании графика
  запоминает *собственный* инлайн-стиль canvas и дословно восстанавливает
  его при `destroy()`. Если в момент создания canvas был скрыт через
  `v-show="false"` (то есть у него уже стоял `display: none`), это значение
  запоминается навсегда — при каждом следующем `destroy()` + `new Chart()`
  Chart.js возвращает `display: none` обратно, независимо от реальных
  данных (его собственный фолбэк `style.display || 'block'` не срабатывает,
  потому что непустая строка `'none'` истинна). Именно так проявлялся баг
  "график сравнения по сетям ничего не показывает, хотя данные приходят" —
  воспроизведено и подтверждено через headless Chromium.
- Полноценный e2e-запуск (docker compose up, реальный MongoDB) не выполнялся в
  среде разработки — сеть песочницы блокирует произвольные хосты, включая
  `fastdl.mongodb.org`, откуда `mongodb-memory-server` скачивает бинарник
  MongoDB для тестов. Код проверен статически (backend — `node --check` по
  всем файлам, frontend — успешный `vite build`) и юнит-тестом
  `stationParser.js` на реальном примере ответа API. Перед боевым
  использованием рекомендуется прогнать `docker compose up --build` в
  окружении с обычным доступом в интернет. По той же причине агрегации
  `metricsService.js` (`$group`, `$dateTrunc`, `$dateToParts`) не выполнялись
  против реальной MongoDB — синтаксис стандартный и соответствует
  документации (MongoDB 5.0+, образ `mongo:7` его поддерживает), но перед
  боевым использованием стоит свериться на реальных данных. Отдельно от
  Mongo-агрегаций логика подсчёта отключений/MTTR (`computeOutages`, чистый
  JS) юнит-протестирована.
- Для больших районов (много станций) снимок на слайдере грузится через
  агрегацию Mongo; при значительном росте объёма данных стоит добавить TTL
  или архивацию старых `StationSnapshot`.
- Точная семантика статусов (`available`/`maybe_available`/`not_available`/
  `no_data`) официально не документирована источником — использована
  напрямую как есть, без дополнительной интерпретации.
- Экспорт анимации (`leaflet-image`) захватывает тайлы карты через `<canvas>`,
  а для этого браузер должен получать тайлы OpenStreetMap с CORS-заголовками
  (`crossOrigin: true` уже включён на слое тайлов). Публичные тайлы OSM это
  поддерживают; если тайловый сервер будет заменён на другой, у него тоже
  должен быть настроен `Access-Control-Allow-Origin`, иначе `<canvas>`
  окажется "tainted" и захват изображения упадёт с ошибкой безопасности.
  Сами механизмы кодирования проверены в headless Chromium в этой среде
  разработки: `gif.js` + Web Worker дал валидный `GIF89a`-файл, а
  `MediaRecorder` с `canvas.captureStream(0)`/`requestFrame()` — валидный
  `video/webm`. End-to-end проверка с реальными тайлами карты не выполнялась,
  так как сеть песочницы не пропускает `tile.openstreetmap.org`.
- Плашка атрибуции на карте (`map.attributionControl.setPrefix(false)`)
  убирает только фирменную ссылку "Leaflet" — это дефолт библиотеки, а не
  требование лицензии. Атрибуция "© OpenStreetMap contributors" от тайлового
  слоя намеренно оставлена как есть: она обязательна по Tile Usage Policy
  OpenStreetMap для их бесплатных тайлов (лицензия данных ODbL). Если тайлы
  когда-нибудь заменят на платного провайдера (Mapbox, MapTiler и т.п.) —
  нужно будет прописать его собственные требования к атрибуции в `attribution`
  соответствующего `L.tileLayer`.
- Видео-запись идёт в реальном времени (частота кадра равна заданной
  задержке между кадрами), а не мгновенно, как GIF — при 20 кадрах и 600 мс
  задержки это ~12 секунд плюс время на запросы снимков; панель экспорта
  показывает примерную оценку длительности.
- Копирование видео в буфер обмена браузеры не поддерживают в принципе
  (проверено эмпирически: `navigator.clipboard.write()` с `video/webm`
  бросает `NotAllowedError` даже в актуальном Chromium, `ClipboardItem.supports('video/webm')`
  возвращает `false`) — это ограничение платформы. Вместо этого используется
  `navigator.share()` (Web Share API) там, где браузер/ОС её поддерживают
  (реалистично — Android Chrome и часть десктопных конфигураций; в headless
  Linux, где тестировалось, `navigator.canShare` не определён), либо обычное
  скачивание файла для последующего прикрепления в Telegram.
- Модель `AdminUser` переименована в `User` (добавлено поле `role`). Для уже
  существующих деплоев это означает смену имени коллекции MongoDB с
  `adminusers` на `users` — старые учётные записи не мигрируются автоматически.
  Проще всего пересоздать администратора: задать `ADMIN_USERNAME`/
  `ADMIN_PASSWORD` в `.env` и перезапустить бекенд — при старте он снова
  засеет админа (см. `ensureSeedAdmin`), если пользователя с таким логином ещё
  нет в новой коллекции.
- Роль в JWT-payload не считается источником истины: `requireAuth` на каждый
  запрос подгружает пользователя из БД по `sub` из токена и берёт роль
  оттуда, а не из самого токена. Это сделано намеренно — иначе смена роли
  или удаление пользователя админом не подействовали бы, пока не истечёт
  токен (`JWT_EXPIRES_IN`, по умолчанию 12 часов), и токены, выпущенные до
  появления системы ролей (без поля `role` в payload), молча читались бы
  как `viewer` вместо честной ошибки авторизации. Один лишний запрос к
  MongoDB на каждый API-вызов — приемлемая цена для небольшой админки.
  На фронтенде `App.vue` при загрузке страницы дополнительно дергает
  `GET /api/auth/me`, чтобы обновить закешированную в `localStorage` роль,
  если она успела устареть.
- Пароли прокси (`Proxy.password`) хранятся в MongoDB в открытом виде, не
  хешированы и не зашифрованы — в отличие от паролей пользователей. Это
  осознанный компромисс: прокси-пароль нужен бэкенду в исходном виде, чтобы
  подключаться к самому прокси-серверу (в отличие от пароля пользователя,
  который только сравнивается через `bcrypt`, а не используется повторно). В
  API-ответах пароль никогда не возвращается (только флаг `hasPassword`), но
  при прямом доступе к базе он читаем. Для продакшена с недоверенным доступом
  к MongoDB стоит добавить шифрование поля на уровне приложения.
- Логика ретраев/автоотключения прокси (`tbankClient.js`, `proxyService.js`)
  проверена мокнутыми юнит-тестами (случайный выбор с исключением уже
  использованных, ранний выход при успехе, авто-отключение строго на пороге
  `PROXY_FAILURE_THRESHOLD`, откат на прямое соединение при отсутствии
  активных прокси) и Playwright-сценарием для страницы «Прокси» в админке
  (добавление/проверка/вкл-выкл/удаление, скрытие для роли viewer, пароль
  нигде не светится в разметке страницы). Против реального SOCKS5/HTTP-прокси
  или реального `toplivo.tbank.ru` это не проверялось — сеть песочницы не
  даёт исходящих подключений на такие хосты; агенты (`https-proxy-agent`,
  `http-proxy-agent`, `socks-proxy-agent`) — стандартные, широко используемые
  пакеты, но перед боевым использованием стоит добавить хотя бы один реальный
  прокси и нажать «Проверить».
- Telegram-бот (`telegramBot.js`, `telegramNotifier.js`,
  `telegramDigestScheduler.js`) проверен статически (`node --check`) и
  end-to-end на уровне страницы админки в headless Chromium против мокнутого
  бэкенда (загрузка статуса/списка чатов, редактирование районов/событий/
  фильтров/вотчлиста, поиск и добавление станции в вотчлист, сохранение,
  тестовое сообщение, удаление чата). Против реального Telegram Bot API это
  проверено на живом боте: изначальная реализация содержала критичный баг —
  `await bot.launch()` для long polling **не резолвится, пока бот работает**
  (`Polling.loop()` внутри `telegraf` крутится вечно), а вызывался он
  последовательно перед `app.listen()` в `index.js`. На практике это значило,
  что весь бэкенд вообще не поднимал HTTP-сервер, как только был задан
  `TELEGRAM_BOT_TOKEN` — сам бот при этом успевал ответить в личку (это
  происходит внутри того же вечного `launch()`), что маскировало проблему,
  пока не выяснилось, что вообще все `/api/*`-запросы недоступны. Исправлено:
  `bot.launch()` теперь не дожидается (`.catch()` без `await`), поэтому
  `app.listen()` выполняется сразу, а статус бота (`GET /api/telegram/status`)
  берётся из `bot.botInfo`, которое `telegraf` заполняет при успешном
  подключении, а не живым запросом `getMe()` на каждую загрузку страницы.
  Живое тестирование также выявило, что часовая и дневная сводки всегда
  писали «нет данных за этот период» независимо от реальных данных:
  `sendDigest` передавал в `metricsService.getStationMetrics` границы
  периода как ISO-строки (`from.toISOString()`), а не `Date` — везде
  остальные вызовы этой функции (`metrics.controller.js`) передают `Date`.
  MongoDB при сравнении по типу BSON ставит `Date` строго выше `String`, так
  что `$lte` с строкой против Date-поля (`polledAt`) не совпадает вообще ни
  с одним документом — агрегация всегда возвращала пустой результат.
  Исправлено передачей настоящих `Date` объектов, как и везде в остальном
  коде.
- Уведомления о появлении/исчезновении топлива — только текст с эмодзи, без
  изображений (картинки есть только у часовой/дневной сводки, см. выше).
  Карточка станции (карта → «Подробная информация» → «Скопировать в буфер»)
  в Telegram-уведомления не встраивается — это по-прежнему отдельная,
  сознательно отложенная задача, не относящаяся к сводкам.
- Рендеринг картинок сводки (`telegramDigestImage.js`, SVG → PNG через
  `sharp`) проверен только в среде разработки (glibc, с системными
  DejaVu/FreeFont шрифтами) — кириллица и все проверенные состояния карточки
  (рост/падение/без данных/100%/длинное название района) отрендерились
  корректно, скриншоты сверены визуально. Внутри реального образа бэкенда
  (`node:20-alpine`) это не проверялось: сеть песочницы блокирует загрузку
  образов с Docker Hub (`production.cloudfront.docker.com`) той же политикой,
  что не пускает `mongodb-memory-server` и запросы к `api.telegram.org` —
  собрать и запустить сам `backend/Dockerfile` для реальной проверки было
  нельзя. `sharp` официально поддерживает Alpine/musl готовыми бинарниками
  без нативной сборки уже несколько лет, а `Dockerfile` ставит `fontconfig` +
  `ttf-dejavu` (тот же шрифт, что проверен локально) — это стандартная,
  задокументированная самим `sharp` конфигурация для Alpine, но перед боевым
  использованием стоит один раз явно проверить `docker compose up --build` и
  посмотреть на реально пришедшую в Telegram картинку сводки.
- Прогнозные Telegram-алерты (`telegramPredictiveAlerts.js`) проверены
  мокнутыми юнит-тестами на синтетических данных (bulk-агрегация профилей по
  нескольким станциям сразу, отсечение по порогу/окну восстановления,
  кулдаун — включая случай "станция уже прошла бы по порогу, но ещё в
  кулдауне после недавнего алерта"), а не против реальной MongoDB — по той
  же причине, что и остальные Mongo-агрегации в проекте (см. выше про
  `metricsService.js`). Пороги (30% на 2 часа вперёд для алерта о пропадании,
  окно в 1 час для алерта о восстановлении, трёхчасовой кулдаун) — начальные
  значения по здравому смыслу, а не подобранные на реальных данных; вероятно,
  потребуют калибровки после того, как станет видно, как часто и насколько
  метко они срабатывают на практике.
- Меню самостоятельной настройки (`telegramSettingsMenu.js`) проверено
  функциональным тестом с мокнутыми `TelegramChat`/`Region`/`Station`
  (заменены прямо в `require.cache`, так что тест гоняет настоящий модуль
  как есть, без правки исходников под тест) и фейковым `bot`/`ctx`,
  фиксирующим все ответы/правки сообщений — не против реальной MongoDB или
  живого Telegram (оба недоступны в песочнице: у Mongo нет ни поднятого
  `mongod`, ни возможности скачать бинарник через `mongodb-memory-server` —
  `fastdl.mongodb.org` отдаёт 403 через прокси песочницы; реальный Telegram
  Bot API, как и везде в проекте, тоже недоступен исходящим соединением).
  Тест прогоняет полный цикл: `/settings` в группе получает отказ и не
  трогает БД; в личном чате создаёт запись и открывает меню; переключение
  района/события сохраняется и переотрисовывается с правильной галочкой;
  поиск станции текстом перехватывается веб-хуком, находит совпадение по
  имени и не находит по нерелевантному запросу, а обычная (не поисковая)
  реплика по-прежнему проходит дальше по цепочке обработчиков; самоактивация
  проходит полный цикл `pending → active → disabled → active` по нажатиям
  одной и той же кнопки. Отдельно проверено, что название района/станции в
  тексте сообщения-меню (единственное место, где это распарсилось бы как
  HTML из-за `parse_mode: 'HTML'`) экранируется, а в подписи кнопки — нет
  (кнопки Telegram не парсят HTML, экранировать там нечего).
